# План на 1–3 дня

## День 1: сначала доказать, что можно собрать данные

Отведите первые 2–4 часа исследованию источника. Самый большой риск — полнота выдачи и защита, а не Laravel/Vue.

1. Выберите несколько реальных карточек: без отзывов, с 1–10, с 100+, с 600+; добавьте недоступную карточку. Зафиксируйте ссылку, время и показанные рейтинг / число оценок / число отзывов раздельно.
2. В DevTools → Network включите Preserve log, фильтр Fetch/XHR. Откройте вкладку отзывов, меняйте сортировку, скролльте именно контейнер отзывов. Найдите начальный JSON и следующие порции. Не угадывайте endpoint по старой статье.
3. Выясните: ID карточки, стабильный ID отзыва, cursor/offset, признак конца, page size, порядок сортировки, обязательные заголовки, cookies и время жизни токенов. Сохраните обезличенные примеры ответов вне публичного репозитория, затем подготовьте минимальные fixtures без секретов.
4. Отдельно найдите три показателя организации. Сокращённое «1,2 тыс.» не является точным числом. Нужны точные числовые поля. Нельзя заменять количество оценок количеством отзывов.
5. Напишите отдельный исследовательский Playwright-скрипт: открыть URL, слушать `page.on('response')`, фильтровать ответы по схеме и ID организации, скроллить контейнер, дожидаться обработки pending JSON promises. Сначала докажите на большой карточке, что извлекаются все доступные уникальные ID.
6. Фиксируйте причину остановки: источник подтвердил конец, подтверждённый лимит доступности, повторный cursor, timeout, CAPTCHA. Ориентир ~600 не должен быть жёсткой константой завершения. Ответ «получено 50 при счётчике 700» без признака конца — частичный результат.

Результат дня: воспроизводимый сборщик с понятной границей полноты. Если источник блокирует сбор на серверном IP, выясните это сегодня, до полировки UI.

## День 2: встроить в существующий каркас

1. Реализуйте `OrganizationParser` новым адаптером. Для Node-сборщика предпочтительно CLI с JSON stdout и stderr для диагностики; запуск через Symfony Process с массивом аргументов (без shell interpolation), timeout и лимитом размера ответа. Альтернатива — закрытый browser-service в Docker network с внутренней авторизацией.
2. Адаптер принимает только канонический URL; сопоставляет ответ с ожидаемой организацией; возвращает поля, которые сейчас показывает `ScaffoldParser`. Расширьте DTO метаданными полноты. Не путайте успешный JSON parse и успешный сбор.
3. Добавьте resolver коротких ссылок: разрешённые хосты, максимум редиректов, проверка каждого Location и DNS/IP, запрет private/loopback/metadata адресов, запрет произвольных портов. Сейчас URL resolver вообще не делает сетевых запросов. Для browser-service также продумайте egress restrictions.
4. Добавьте типизированные ошибки `blocked`, `unavailable`, `source_changed`, `partial`, `transient`. Повторять только transient; на CAPTCHA показывать статус, на смене схемы писать диагностику.
5. Добавьте job lock, лимит одновременных браузеров, прогресс по порциям, timestamps начала/завершения, завершение зависших запусков и безопасный повтор. Согласуйте timeout браузера, job и retry_after.
6. Сохраняйте результат целиком после проверки полноты; при ошибке показывайте предыдущие данные как устаревшие. Текущий upsert не удаляет старые отзывы: для точного «последнего доступного набора» добавьте membership `run_reviews` и выдачу по последнему успешному run.

## День 3: доказательства и сдача

1. Fixtures-тесты: изменённая схема, пустой ответ, валидный ноль, повторная порция, дубли между порциями, пропавший cursor, ограниченная выдача, счётчики с разным смыслом, редактирование отзыва, CAPTCHA, 429.
2. Проверка с настоящими cookies: CSRF bootstrap → login → защищённый API → logout → 401. Laravel feature tests обычно отключают CSRF, поэтому они не заменяют этот сценарий в браузере.
3. Smoke test реального Яндекса локально и на хостинге. Сверьте точные счётчики вручную в одно время; зафиксируйте collected и stop_reason. Проверьте страницы 1, 2, последнюю и повторное обновление без дублей.
4. Docker Compose: app/web, queue worker, browser, PostgreSQL, Redis; healthchecks, постоянные volumes, секреты в окружении. Собрать frontend; миграции запускать однократно при релизе, не всеми workers одновременно.
5. Хостинг с HTTPS, `APP_DEBUG=false`, корректным `APP_URL`, secure session cookies и Sanctum stateful domain без схемы. В одном origin проще избежать ошибок CORS/cookie. Настроить supervisor/restart для worker, доступность Chromium, логи и свободную память.
6. Откройте опубликованный URL из чистого браузера, войдите сид-пользователем и подключите новую произвольную карточку. Убедитесь, что worker реально работает после выхода из SSH.
7. Перепишите README по фактической реализации: какие URL поддержаны, проверенные ограничения, инструкция запуска, пункты 1–5, ссылки на хостинг и Git. Оставьте короткий честный список недоделок.

## Приоритет при нехватке времени

Рабочий полный сбор и точные счётчики → очередь и сохранность данных → пагинация и ошибки → хостинг → история и оформление. Не тратьте первый день на дизайн, прокси-ротацию или десятки абстракций до проверки выдачи.
